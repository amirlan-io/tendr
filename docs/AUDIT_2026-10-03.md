## P0 — исправить до открытого запуска

### 1. Гостевой идентификатор пересекается с авторизованным

`backend/app/core/client_id.py:33` принимает cookie/header клиента без токена. `backend/app/core/supabase_auth.py:117` строит авторизованный ID из Supabase UUID. Валидатор допускает этот же формат для гостя. Поэтому знающий UUID пользователя запрос может выдать себя за него в маршрутах, использующих `require_client_id`, включая историю и скачивание документов. Проверена коллизия resolver на вымышленном ID; чужие записи не запрашивались.

Нужно: разделить гостевые и авторизованные идентификаторы, требовать проверенный токен для аккаунтных данных, отклонять зарезервированные форматы у гостей. Добавить отрицательные тесты cookie/header без токена для истории, документов, квот. Маршруты поставщиков с `require_supabase_user` отдельно защищены и автоматически под эту находку не подпадают.

### 2. Дорогие операции имеют обход учёта и ограничения доступа

`backend/app/api/lots.py:292` допускает `with_ai` без зависимости авторизации/резервирования квоты; `backend/app/api/products.py` предоставляет search/deep-search без авторизации. Поиск поставщиков требует входа, но в его handler не видно резервирования пользовательской AI-квоты. Общего ограничения запросов для этих маршрутов в приложении не обнаружено; отдельный limiter у browser actions не решает эту проблему.

Нужно: единая политика авторизации, стоимости и лимитов для всех обращений к LLM/Tavily/Browser; предел конкурентных запросов; идемпотентность повторных запусков; контролируемая выдача бесплатной квоты гостю. Возможные ограничения на внешнем reverse proxy отдельно не проверены.

### 3. Неполная проверка выглядит успешной

`web/src/pages/Analyze.tsx:524` и `:555` окрашивают любой риск, кроме high/medium, в зелёный. `web/src/dashboard/pages/Overview.tsx:65` подписывает прочие состояния как «Проверено». `backend/app/services/orchestrator.py:207` при `needs_review` может вернуть «участвовать» по trust/margin.

Нужно: отдельное состояние «Недостаточно данных / требуется проверка» на всех экранах; запрет положительной рекомендации при неполной юридической проверке; явное указание, какие документы прочитаны и какие проверки не выполнены.

### 4. Выявленные риски теряются при сохранении

`backend/app/api/lots.py:427` записывает `str(red_flags)`, а `:203` читает через `json.loads`. Для обычного непустого списка строк это несовместимые форматы. Пользователь может получить пустой список при наличии рисков.

Нужно: JSON-сериализация или JSON-колонка, проверка существующих записей и повторный анализ/миграция по необходимости; тест полного цикла сохранения и чтения.

### 5. Локальные данные не изолированы по аккаунтам

`web/src/dashboard/dashboard.data.ts:65` хранит сохранённые лоты и документы под общими ключами localStorage. `web/src/historyStore.ts:24` использует общий ключ истории. `AuthContext` при выходе их не очищает. При смене пользователя в том же браузере остаются прежние локальные данные; при недоступном сервере история показывает общую локальную копию.

Нужно: ключи по user ID, очистка состояния при выходе/смене аккаунта, серверное хранение избранного и документов. Проверка двумя тестовыми аккаунтами и на втором устройстве обязательна.

## P1 — завершить основной рабочий сценарий

### 6. Поиск не равнозначен полному каталогу

- `Lots.tsx:275`: сортировка только массива текущей страницы (запрос загружает 20 лотов), а не всех найденных результатов. «Сначала крупные» не означает самые крупные во всём реестре.
- `graphql_client.py:159`: UI называет фильтр датой публикации, но запрос фильтрует `indexDate`, при этом `publishDate` отдельно присутствует в данных объявления. Требуется согласовать семантику с API и проверить на конкретных объявлениях.
- Для категории/префикса региона сканируются максимум пять страниц по 200 записей; точный общий счётчик для этих запросов не вычисляется (это отмечается `total_is_exact=false`).
- `Lots.tsx:662`: кнопки следующей страницы находятся только внутри ветки непустой выдачи. Если локальная фильтрация убрала все записи, но `has_more=true`, пользователь не может перейти дальше.
- `lots.py:322`: просроченные записи дополнительно удаляются после запроса, но общий счётчик может остаться исходным и точным по флагу. Нужно согласовать счётчик и фактическую выдачу.

Нужно: серверная сортировка/индекс каталога, корректная семантика дат, работающая пагинация даже при пустой странице, честные счётчики. Проверить набор сценариев: сайт, разработка сайта, мебель, фильтры, номер лота, БИН, регион, архив и пересечение фильтров.

Уже реализовано: активные статусы по умолчанию, архив через статус, исключение известных истёкших сроков, исправленная срочность, cursor-пагинация и отметки обновления. Не нужно повторно ставить это как полностью отсутствующие функции.

### 7. Новый ползунок неудобен для малого бизнеса

`Lots.tsx:80`: шаг составляет 50 000 000 ₸. После удаления точных полей ввода нельзя выбрать бюджет 500 тыс., 2 млн или 10 млн ₸. При верхнем положении UI показывает 49,5 млрд, но запрос отправляет 0 (без ограничения).

Нужно: сохранить чистый новый дизайн, добавить компактный точный ввод по нажатию на сумму, удобную шкалу/предустановки для небольших бюджетов и честное отображение режима «без ограничения». Этот недостаток затрагивает и последнее изменение фильтра.

### 8. История не позволяет нормально продолжать работу

`lots.py:511` возвращает total как длину максимум 50 записей. При большей истории frontend может прекратить пагинацию раньше времени. Серверная запись истории не содержит URL, а `History.tsx:152` показывает ссылку на анализ только при наличии URL. При локальной ссылке анализ запускается заново (`Analyze.tsx:114`) вместо открытия сохранённого результата. В `Documents.tsx:143` ссылка ведёт просто на пустую страницу анализа.

Нужно: отдельный analysis ID, GET сохранённого результата, маршрут `/dashboard/analyses/:id`, настоящий COUNT, раздельные действия «Открыть» и «Повторить анализ» с показом стоимости повтора.

### 9. Загруженные документы не проходят весь жизненный цикл

`Documents.tsx:26` допускает скачивание только при числовом lot ID; endpoint download также принимает int. Анализы загрузок с нечисловым ID выпадают из этого пути. Раздел хранит список скачиваний локально, а не полноценную библиотеку файлов.

Нужно: привязка отчёта к analysis ID независимо от происхождения; серверная библиотека с владельцем, исходным файлом, датой и версиями результата; повторное скачивание с другого устройства. OCR-код существует, но его внешняя работоспособность не подтверждена; `mistralai` используется импортом и не объявлен в `backend/pyproject.toml`.

### 10. Долгий анализ не оформлен как сохраняемое задание

Основной анализ ждёт результат в одном HTTP-запросе и хранит состояние ожидания в React. Поиску поставщиков также приходится ждать цепочку внешних вызовов. Нет подтверждённого сценария «закрыл вкладку → вернулся к статусу задания».

Нужно: серверное задание с ID и состояниями, прогресс по фактическим этапам, повтор после ошибки, восстановление после перезагрузки, понятный таймаут. Не обещать точное время без измерений на реальных документах.

### 11. Доверие к заказчику и маржа — эвристики

`services/scoring.py:24` задаёт фиксированные проценты по словам категории; trust вычисляется из собственных сохранённых анализов по похожему имени заказчика. Это не подтверждённая прибыль конкретного поставщика и не полная история исполнения договоров заказчика.

Нужно: явная маркировка оценки, основание и объём данных; для прибыли — себестоимость, доставка, налоги, монтаж, обеспечение и резерв; для заказчика — надёжный идентификатор и проверяемые источники. Не использовать эвристику как достаточное основание решения об участии.

### 12. Кабинет пока не является единым проектом закупки

Навигация связывает разделы, но в основном есть история анализов, локальное избранное и список документов. Главная обещает связанный проект с подготовкой к подаче. Не обнаружен завершённый пользовательский путь с ответственными, статусами подготовки, отмечаемым чек-листом, задачами и результатом участия.

Нужно: карточка закупки как центр работы — источник, анализ, требования, документы, поставщики, сроки, заметки и следующий шаг. Командные роли и приглашения можно вынести после одиночного рабочего сценария.

### 13. Статистика кабинета может вводить в заблуждение

`Overview.tsx` суммирует требования и риски только загруженной первой страницы истории, но подписывает «Всего». Счётчик дедлайнов берётся из списка, обрезанного до пяти, включая overdue; заголовок говорит «Активных».

Нужно: агрегаты с сервера, отдельные активные/просроченные сроки, подписи периода и объёма данных. Лента активности собирается блоками, а не общей сортировкой по времени.

## P2 — коммерческий запуск и качество продукта

### 14. Оплата и тарифная логика не завершены

`Billing.tsx:37` отключает покупку. Backend учитывает месячную квоту; заявленных на главной пятичасовых окон в проверенном коде не найдено. Нет подтверждённого платёжного пути с активацией тарифа, webhook, повторной оплатой и возвратом. `renewsAt` в кабинете передаётся null.

Для бесплатного пилота: назвать режим пробным и объяснить фактический лимит/дату обновления. Для платного: реализовать единый каталог тарифов на сервере, ledger расходов, idempotent webhook и тестовый платёжный цикл. Это не блокирует бесплатный пилот после P0, но блокирует продажу описанной подписки.

### 15. Письма и звонки поставщикам ещё не подключены

`services/outreach.py:102` использует DisabledEmailProvider/DisabledCallProvider. Черновики, очередь одобрений и политика отправки есть; считать реальную рассылку/звонки готовыми нельзя.

Нужно: адаптеры провайдеров, статусы доставки/звонка, защита от дублей и учёт стоимости, доступный UI одобрения. Для раннего пилота достаточно поиска поставщика и копируемого черновика с ручной связью.

### 16. Авторизация требует отдельной сквозной приёмки

Email/password, Google callback, восстановление и защита dashboard реализованы. Нельзя по этому аудиту заявить, что прежняя Google 500 исправлена: реальные настройки Supabase/Google и вход не проверены. В AuthContext обработка getSession не содержит catch; в Google-handler нет try/finally на неожиданный сбой.

Нужно: проверить создание аккаунта, повторный вход, Google, восстановление, истечение сессии и выход; обработать сетевые ошибки без вечной загрузки; сохранять исходную целевую страницу после авторизации.

### 17. Главной не хватает доказательства результата

На первом экране уже понятно, для кого продукт и зачем он нужен. Но посетитель видит преимущественно обещания, анимации и регистрацию; полноценного открываемого примера готового разбора нет. Публичные сценарии поставщика уводят на standalone analyze, а основные CTA — на регистрацию, что делает вход в продукт неоднородным.

Рекомендация: второе действие «Посмотреть пример разбора» с явно помеченным примером, краткое объяснение бесплатного доступа, реальный результат с источником и ограничениями, FAQ о документах/сроках/данных. Следующее улучшение дизайна — понятный результат и навигация, а не дополнительная анимация.

### 18. Дизайн и доступность требуют унификации

Dashboard использует чёрные панели, History — slate/green карточки, Analyze — другой набор цветов и компонентов. Объединить состояния загрузки, ошибки, пустых результатов, кнопки и карточки; отдельно проверить контраст мелких подписей, клавиатурный фокус и touch-управление ползунком. Нельзя считать мобильную приёмку завершённой на основании адаптивных CSS-классов.

### 19. Не хватает страницы доверия и поддержки

В маршрутах и footer не обнаружены страницы контактов поддержки, условий использования и политики данных. Это продуктовая находка, а не юридическое заключение. До публичного запуска нужны реальные контакты, объяснение хранения загружаемых документов, срока удаления и способа обращения; тексты должны соответствовать фактическому устройству продукта.

### 20. Эксплуатация и совместная разработка

- В проверенной ветке нет `.github` workflows: автоматический gate тестов/сборки в репозитории не обнаружен.
- README описывает устаревшие состояние и стек; перечисляет как готовое то, что ещё требует приёмки.
- Настройка Sentry есть, её инициализация в текущем приложении не обнаружена. В ветке друга уже есть отдельная работа над error reporting — сначала объединить и проверить её, не дублировать.
- Все страницы импортируются статически; крупный общий JS можно разделить по маршрутам. Реальные показатели загрузки и Core Web Vitals не измерялись.
- Нужны единый staging, стабильный запуск backend, мониторинг API Госзакупок/LLM/БД, резервные копии с проверкой восстановления, контроль расходов и smoke-тест после деплоя. Наличие внешней инфраструктуры за пределами репозитория не проверено.
- Ключи и пароли ранее публиковались в чате; их ротация не проверялась. До внешнего запуска проверить отзыв именно раскрытых credentials, не переносить их в код или отчёт.

## Рекомендуемый порядок выполнения

1. Объединить четыре новых коммита друга в рабочую ветку через обычный merge/PR и повторить релевантные проверки. Назначить одного владельца поиска/анализа и одного владельца supplier-сценария.
2. Закрыть P0: идентификация, платные операции, неполные результаты AI, сериализация рисков, изоляция локального состояния.
3. Завершить поиск: мелкие бюджеты, сортировка, дата, пустые страницы, счётчики; сверить 10–20 публичных лотов с первоисточником.
4. Реализовать сохранённый анализ и проект закупки: открыть без повторного списания, продолжить подготовку, скачать результат после загрузки файла и с другого устройства.
5. Провести сквозную приёмку входа и пилот с несколькими реальными поставщиками. Измерять время до первого полезного анализа, долю успешных разборов, возвраты пользователей, расхождения и себестоимость.
6. После устойчивого бесплатного сценария подключать оплату, автоматические уведомления, email/call провайдеров и командную работу.

## Условия готовности пилота

- Гость не может подставить авторизованный ID; два аккаунта не видят локальные данные друг друга.
- Любая платная операция учитывает квоту и ограничение запросов.
- «Нет данных» никогда не означает зелёную проверку или рекомендацию участвовать.
- Пользователь находит актуальный лот, получает проверяемый разбор, сохраняет и открывает его без нового анализа.
